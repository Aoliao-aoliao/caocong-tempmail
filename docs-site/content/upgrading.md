# 更新与恢复

版本检查只是提示。普通代码提交不会自动成为正式版本，安装环境也不会因为收到提示就自动部署。

1. 阅读对应版本的更新说明，确认是否涉及数据库迁移。
2. 为自己的数据库、`.env`、附件和 TLS 准备可恢复的备份。
3. 取得明确版本的源码，构建一个新的镜像标签，不复用正在运行的标签。
4. 回到原安装目录，执行：

```bash
node manage.mjs check
node manage.mjs upgrade --image nodemail-local:NEXT_VERSION
```

当前工具先核对原主密钥、迁移文件名及摘要，再更换镜像并等待健康检查；成功后更新 `.active-image`。激活失败会尝试恢复原镜像，若恢复也失败会明确报错，需要检查 Docker 日志。

数据库结构变化时校验会拒绝升级；该版本必须附带专门的迁移流程。不要执行 `db:init` 或删除数据卷以绕过保护，也不要用新的 `.env` 覆盖旧配置。新源码目录里的模板不是旧站配置的替代品。

当前提供源码发行，镜像由安装者自行构建。更新公告由同一仓库的文档站发布；修改代码不自动升级用户实例。

## 后台什么时候提示更新？

管理员打开后台后会检查版本，页面保持打开时每 15 分钟检查一次；服务器成功结果缓存 6 小时。点击“检查更新”可主动刷新，至少间隔 1 分钟。

只有发布者发布正式 GitHub Release，且版本验证和公告发布成功，才会出现新的稳定版本通知。草稿、测试版和普通代码提交不会变成更新提示。网络不通时显示检查失败，不影响收信，也不会假装已经是最新版。

更新公告只有版本号、发布时间和说明，不包含任何站点的用户、邮件、订单或配置。后台不会自动下载安装，更不会覆盖自己的数据库。按本文步骤在原安装目录升级；原 `.env`、主密钥和数据卷必须保留。

## 项目维护者如何发版？

1. 在同一仓库修改应用和文档，提升 `package.json` 的版本并同步锁文件；通过 PR 的安装、权限和数据保留测试后合并。
2. 作者自用站由 `Deploy owner website` 更新，部署凭据只在受保护的 `production` 环境内；普通安装者不需要配置这条流水线。
3. 在 GitHub 创建对应 `vX.Y.Z` 的正式 Release，标签必须指向该版本提交，填写升级说明。版本号与源码不一致会阻止公告发布。
4. `Documentation` 工作流验证正式版本，从 Release 生成公告并发布文档站。之后各安装站通过自己的后台获取通知。

不需要手工修改 `stable.json`，也不要上传自己的 `.env`、数据库导出或服务器目录作为发行附件。数据库结构变更需要单独提供迁移方案，现有安装器会拒绝直接替换不兼容结构。
