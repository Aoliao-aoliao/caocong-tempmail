# 备份自己的数据

下载一份源码不是备份网站。源码不包含你的用户、邮件、积分和订单；真正需要备份的是安装后产生的数据和配置。

## 哪些东西要一起保留？

| 内容 | 在哪里找 | 丢失会影响什么 |
| --- | --- | --- |
| 安装配置 `.env` | 原项目的 `installer` 目录，注意显示隐藏文件 | 数据库连接、主密钥和接入配置 |
| `.active-image`（如有） | 同一安装目录 | 当前启用的程序版本记录 |
| MySQL 数据 | 本项目 database 数据卷 | 用户、订单、积分、邮件记录及后台配置 |
| 邮件附件 | 本项目 attachments 数据卷 | 原有邮件的附件 |
| SMTP TLS 文件（如有） | 安装目录 tls | SMTP TLS 服务 |
| 当前源码版本和镜像标签 | 部署记录、本机镜像 | 按原版本恢复与回滚 |

数据卷名称带有本次安装的项目名前缀。在 1Panel 容器详情里看 app 和 db 的挂载，确认它们实际使用的卷；不要根据“看起来像”就选择其他项目的数据卷。

## 用 1Panel 的网站备份够不够？

不一定。反向代理网站目录主要是网站代理相关文件，草丛临时邮箱 数据在 Docker 数据卷中。只备份网站目录，可能根本没有备份邮件和数据库。

1Panel 数据库页面如果没有管理这个 Compose 创建的 MySQL，也不能假定它的数据库备份任务包含 草丛临时邮箱。

## 建议怎样安排？

根据可以接受丢失多久的数据确定周期，并在每次升级前另存一份。至少留一份在其他存储位置，不能只放在同一块服务器磁盘上。

数据库使用支持 MySQL 一致性导出的备份方式；不要直接压缩正在写入的 MySQL 数据目录作为唯一备份。若需要数据库与附件严格对应的恢复点，应安排维护窗口暂停应用写入，或采用经过验证的协调备份流程。

本文没有提供一条通用恢复命令，因为恢复会覆盖目标环境，必须先确认目标库、卷名和旧版本。不要把生产数据直接导进一个已经有用户的新安装中。

## 怎样判断备份可用？

“文件下载成功”只能说明保存了文件。可靠的验收是在隔离环境恢复，使用同一版本程序和对应的 `.env`，检查管理员登录、用户记录、订单和样本附件。

恢复测试时关闭真实支付、OAuth 回调和中继轮询等外部动作，避免测试站连接真实业务。测试完成清理测试环境，保留恢复步骤与测试日期。

## 这些操作不要当作清理空间的方法

- 删除数据库卷或附件卷后重建容器。
- 重新生成 `.env` 来处理密钥错误。
- 删除订单、积分流水或业务防重复表。
- 把 `docker system prune --volumes` 当作日常维护命令。

需要释放空间时，先确认占用来源。审计日志可用后台的保留策略处理；旧备份和旧镜像是否可删，应在确认不再用于恢复后逐项决定。
